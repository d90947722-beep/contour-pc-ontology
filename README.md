# Контур 2.4 — онтология совместимости компьютерных комплектующих

Приложение для проверки компьютерной сборки перед покупкой, выбора замен и подбора новой конфигурации. Основа проекта — формальная модель OWL, объяснимые проверки и источники характеристик производителей.

## Что добавлено в версии 2.4

- Готовый сценарий «Память и питание: две замены»: несовместимая DDR4 и БП 400 Вт. Для поиска уже выбраны RAM и БП, остальные шесть деталей закреплены. Пример использует учебные цены, чтобы результат не зависел от ранее введённых цен.
- При изменении цели, бюджета, состава и других параметров поиска старые варианты скрываются. Приложение объясняет, что нужно пересчитать поиск; применить устаревший план нельзя.
- Верхний счётчик и главный статус печатного отчёта отражают совместимость оборудования. Превышение бюджета выводится отдельно и не увеличивает число конфликтов оборудования. Низкоуровневый `engine.validate` сохраняет прежний контракт для поиска и экспорта OWL.
- В боковой панели и печатном отчёте показаны версия и идентификатор снимка кода и онтологии. Он позволяет сравнить локальную и опубликованную сборки.
- Длинные пояснения и подписи переносятся в узком окне. Таблицы сохраняют штатную прокрутку.

### Изменения предыдущей версии 2.3

- Три пользовательских сценария: «Проверить сборку», «Обновить компьютер», «Собрать с нуля».
- Подтверждённые конфликты оборудования отделены от неизвестных условий, отсутствующих деталей и превышения бюджета. Неполный состав не получает статус успешной проверки.
- Из сообщения о конфликте можно перейти к подбору категории. Для замены показаны устранённые конфликты и оставшиеся проблемы всей сборки.
- Цены выбранных деталей вводятся прямо в конфигураторе. Можно скачать памятку перед покупкой, JSON со сборкой и печатный отчёт.
- Для апгрейда выбираются обязательные замены, остальные детали сохраняются по умолчанию. Отдельный бюджет и цель «Минимальные расходы на покупку» учитывают только новые детали, без вычитания предполагаемой продажи старых.
- В публичной версии новый посетитель начинает с пустой конфигурации и реального каталога. Сборки и цены разных сеансов изолированы; для длительного хранения используйте JSON.

### Быстрый сценарий

1. **Проверка перед покупкой:** выберите точные модели в «Проверке сборки», задайте известный BIOS и свои цены. Исправьте конфликты и уточните неподтверждённые условия по ссылкам производителей.
2. **Апгрейд:** укажите текущую конфигурацию, выберите «Обновить компьютер», отметьте обязательные замены и задайте бюджет покупок. Бюджет всей сборки в боковой панели действует дополнительно; отключите его, если нужен только предел расходов на новые детали.
3. **Новая сборка:** выберите «Собрать с нуля», укажите цены кандидатов в «Каталоге», включите бюджет всей сборки и нажмите «Найти варианты». Выбранные детали учитываются только при явной фиксации.

Каталог содержит 32 реальные модели и учебные примеры. Автоматического получения цен магазинов и измерений FPS нет. Если точной модели или характеристики нет, результат не подтверждает совместимость аналогичной детали. Варианты с неизвестными условиями появляются только при включении соответствующего разрешения и сохраняют пометку «Недостаточно данных».

## Запуск

**Windows:** распакуйте архив, откройте `START.bat`. Скрипт запускает сервер в фоне, ожидает его готовности и открывает сайт в браузере. Окно запуска можно закрыть. Повторный запуск открывает уже работающий сайт. В первый раз нужен интернет: скрипт создаст `.venv` и установит зависимости. Нужен Python 3.10+; в исходной папке проекта автоматически используется уже подготовленное окружение. Журналы запуска: `data/server.log` и `data/server-error.log`.

Вручную из папки проекта:

```powershell
py -3 -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe -m streamlit run app.py
```

Для Linux/macOS: `python3 -m venv .venv`, затем используйте `.venv/bin/python`. Локальный адрес напечатает Streamlit; обычно это http://localhost:8501. Доступ ограничен локальным компьютером.

Для логического вывода HermiT нужна Java в PATH. Основные проверки, подбор и SPARQL работают без неё. Для небольшой онтологии HermiT выделяется 512 МБ памяти.

## Как пользоваться

### Качество данных и недостающие сведения

Во вкладке **«Качество данных»** проверьте каталог либо текущую сборку вместе с ним. Формальные ограничения записаны отдельно в `ontology/quality-shapes.ttl` и исполняются pySHACL. Проверяются обязательные поля, кардинальности, типы/диапазоны значений, профили поддержки, источники и структура оценок сборки.

SHACL проверяет записанный снимок, а HermiT — логическую согласованность OWL и вывод классов. Эти механизмы дополняют друг друга. Отсутствующий обязательный сокет — нарушение формы данных; неизвестная необязательная пиковая мощность — не нарушение формы и остаётся неизвестным условием совместимости.

Результат проверки структуры не означает, что сборка физически совместима или что источник подтверждает истину. Отдельно отображается наличие записей происхождения для значений реальных компонентов и даты сверки источников. Контент сайтов при аудите не запрашивается. Возраст более 180 дней — локальный повод для пересмотра, а не универсальный стандарт достоверности.

В этой же вкладке и в результатах конфигуратора доступен **адресный список уточнений**: конкретная модель, неизвестное свойство, связанные правила, действие и источники для проверки. Повторяющиеся запросы к одному свойству объединяются. При незаданном бюджете отсутствие цен не выдаётся за ошибку совместимости. Подтверждённый конфликт не переименовывается в неизвестность.

### Просмотр живого графа онтологии

Во вкладке **«Онтология и вывод»** откройте «Исследовать реальные связи». Выберите компонент, профиль поддержки, источник или утверждение; настройте один/два перехода, показ значений и происхождения.

Граф строится из фактических отношений Owlready2, включая входящие связи. Таблица показывает полные значения, а RDF-фрагмент можно скачать в Turtle. Отображение ограничено 45 узлами; при обрезке появляется явное уведомление. Это фрагмент графа, а не полная онтология и не отдельный результат HermiT. Зелёным выделен выбранный объект, отдельным цветом — классы и литералы.

### Сохранения без работы с файлами

Во вкладке **«Мои сборки»** задайте название текущей конфигурации и сохраните её. Варианты можно открывать, явно обновлять текущим составом, сравнивать (до трёх одновременно) и отправлять в восстанавливаемый архив.

Последняя корректно введённая конфигурация автоматически сохраняется как черновик и восстанавливается после перезапуска. Именованные сборки не перезаписываются автоматически. Проверки при открытии выполняются заново по текущему OWL, а записанные цены восстанавливаются из снимка.

Цены, сохранённые в каталоге, теперь остаются на компьютере и подставляются при переключении каталогов и готовых сценариев. Загруженная именованная сборка сохраняет свои цены; её открытие не меняет общий список цен.

Хранилище: `data/contour.sqlite3` внутри папки проекта. Здесь находятся сборки, черновик и цены, но не исходные характеристики оборудования. OWL остаётся источником предметных знаний. При переносе проекта переносите папку `data` отдельно либо используйте экспорт JSON. Пользовательская база исключена из Git и распространяемого ZIP.

В нескольких вкладках общий черновик отражает последнее сохранённое состояние. Для независимых вариантов используйте именованные сборки.

### Отчёт для печати

Для именованной сборки включите **«Показать отчёт прямо здесь»**: он откроется внутри приложения с кнопкой печати. Также кнопка **«Отчёт для печати»** скачивает самостоятельный HTML: состав, цены и их тип, все результаты, объяснения и официальные источники. Откройте скачанный отчёт в браузере и нажмите его кнопку печати, чтобы распечатать или сохранить PDF.

Отчёт представляет прикладные проверки, а не результат отдельного запуска HermiT. Экспорт OWL сохранён отдельно.

### Конфигуратор

Слева выберите учебный или реальный каталог. Выбор компонентов автоматически обновляет проверки. Для каждого конфликта доступны правило, причина и исходные значения. Подбор замены относится к выбранной категории: другие конфликты могут сохраниться.

В режиме встроенной графики дискретная GPU не обязательна. При этом нужны подтверждённая встроенная графика процессора и видеовыход платы.

### Реальные модели и цены

В каталоге откройте карточку и таблицу происхождения характеристик: свойство, значение, URL и дата сверки. Полный перечень — `docs/SOURCES.md`.

**Цены реальных компонентов не собраны и не выдуманы.** Во вкладке «Каталог» внесите свои цены и нажмите «Сохранить цены». Они сохраняются на компьютере и в экспортируемой сборке отдельно от сведений производителя. Пустая цена неизвестна; 0 — явно заданная нулевая стоимость. Сумма с неизвестными ценами показывается как неполная («от …»).

Для расчёта бюджета или цели «Минимальная стоимость» поиск допускает только компоненты с известной ценой. Для других целей без бюджета можно искать варианты без цен; их стоимость остаётся неполной.

### BIOS

Учебные платы используют целые ревизии 100/200. Для реальных плат вводится точная строка, например `0602` или `2423`. В каталоге известна минимальная версия поддержки, но **не установленная прошивка конкретной платы**. Поэтому при выборе новой реальной платы поле BIOS остаётся неизвестным.

Точное совпадение с подтверждённой минимальной версией удовлетворяет проверке. Порядок произвольных строк не угадывается: другая версия даёт «недостаточно данных», пока нет проверенной последовательности. Формат способен обрабатывать сведения «поддерживается с любой версии»; в текущем реальном наборе используются точные метки.

### Автоподбор и исправление

- Выберите «Новая сборка» либо «Исправить текущую».
- Задайте цель, бюджет и фиксированные компоненты.
- По умолчанию поиск возвращает только полностью подтверждённые в рамках правил варианты.
- При необходимости включите варианты с неподтверждёнными условиями: они обозначаются отдельно, причины перечисляются.
- Нажмите «Применить вариант» либо скачайте его JSON.

Подтверждённые варианты имеют приоритет перед неизвестными. Поиск ограничен 50 000 узлов и 12 секундами. При достижении предела выводится явное предупреждение: глобальная оптимальность не доказана. При полном обходе с корректными отсечениями оптимум относится **только к выбранному каталогу, целям и фиксированным условиям**.

Количество ядер и объём памяти не заменяют измеренную производительность в играх или программах. Поиск не обещает заданный FPS и не использует непроверенные рейтинги.

## Формальная модель

Файл `ontology/components.owl` — единственный источник характеристик и связей во время работы. Генераторы и seed-файлы нужны для воспроизводимого создания модели; приложение получает факты из OWL через Owlready2.

Предметные классы: CPU, Motherboard, RAM, GPU, PSU, Case, Storage, Cooler. Сокеты, стандарты DDR и форм-факторы представлены отдельными экземплярами понятий. CPUBoardSupport — n-арная связь конкретного CPU, платы, минимального BIOS, статуса и источника.

В OWL определены домены, диапазоны, функциональные свойства, непересечение категорий и различие экземпляров стандартов. Есть один явно отрицательный **учебный** профиль поддержки; отсутствие профиля не считается отрицательным утверждением.

Примеры определений:

```text
DDR5Board ≡ Motherboard ⊓ ∃ supportsMemory.{DDR5}
EvidenceBackedComponent ≡ Component ⊓ ∃ hasSource.SourceDocument
ConflictedBuild ≡ Assembly ⊓ ∃ hasAssessment.FailedAssessment
UncertainBuild ≡ Assembly ⊓ ∃ hasAssessment.UnknownAssessment
VerifiedBuild ≡ PopulatedBuild ⊓ ∃ hasAssessment.PassedAssessment
                ⊓ ∀ hasAssessment.PassedAssessment
```

PopulatedBuild требует компоненты всех восьми категорий либо семь категорий в режиме встроенной графики с подтверждёнными возможностями CPU и платы. Для экспортированного снимка состав и набор оценок локально замыкаются через `only OneOf(...)`; глобальный каталог не переводится в закрытый мир.

**Разделение ответственности:** Python вычисляет проверки и записывает результаты. HermiT проверяет согласованность OWL и выводит классы по этим результатам и структуре. HermiT не пересчитывает мощность, не доказывает истинность сведений производителя и не заменяет прикладной поиск.

JSON-сборки версии 1 продолжают импортироваться; версия 2 дополнительно сохраняет цены пользователя, режим графики и строковый BIOS. Результат из файла не считается доверенным: после импорта проверки выполняются заново.

## Правила

| ID | Ограничение |
|---|---|
| R01 | Сокеты CPU и платы |
| R02 | Профиль поддержки, явная неподдержка и BIOS |
| R03–R05 | Стандарт DDR CPU/платы и форм-фактор памяти |
| R06–R08 | Лимиты объёма памяти и числа модулей |
| R09–R12 | Форм-фактор платы, длина GPU, крепление и высота кулера |
| R13 | Учебный порог охлаждения либо явная поддержка CPU производителем кулера |
| R14 | Форм-фактор БП |
| R15 | ceil((пик CPU + пик GPU + 60 Вт) × 1,25); без GPU её вклад равен 0 |
| R16–R18 | PCIe 8-pin, 12V-2x6 и EPS |
| R19–R21 | Интерфейс накопителя, длина M.2 и питание SATA |
| R22 | Бюджет при известных ценах |
| R23–R24 | Возможность работы без дискретной GPU |
| R25 | Наличие точного номинального размера крепления M.2 |
| R26–R27 | Толщина GPU и зазор над RAM / явное отсутствие перекрытия |
| R28 | Рекомендация производителя GPU по номиналу БП для его эталонной системы |
| R29 | Длина БП при условиях выбранной конфигурации корпуса |
| D01 | Полнота цен при включённом бюджете |

Неизвестное не равно нулю. Если GPU явно не требует определённый тип разъёма, сведения о количестве таких разъёмов БП не нужны для этой частной проверки. Рекомендация производителя GPU — отдельное ограничение прототипа, а не измерение фактической мощности сборки.

## Источники и ограничения

Дата сверки реального каталога: **28 октября 2026 года**. Характеристики — ограниченный снимок официальных данных с условиями конкретных моделей/ревизий.

TDP AMD хранится отдельно от неизвестной пиковой мощности CPU. Паспортное потребление GPU также не подменяет измеренный пик. NSPR Noctua не переводится в ватты. Поэтому реальная сборка может остаться условной даже при корректном сокете и памяти.

Высота RAM в текущем целочисленном формате не округляется вниз из дробных номиналов/допусков. Для кулеров с явной гарантией отсутствия перекрытия DIMM используется отдельное свойство. Неизвестный предел толщины GPU у корпуса остаётся неизвестным. Все такие причины видны в проверках.

Один накопитель и один комплект памяти; нет моделирования произвольной разводки PCIe, одновременного использования нескольких портов, QVL/XMP, переходников, переходных пиков питания и полного трёхмерного размещения. Изменение числа корзин, установка радиатора или снятие кронштейна меняют условия корпуса и требуют отдельной конфигурации.

## Воспроизведение и проверка

```powershell
.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.venv\Scripts\python.exe -m pytest -q
.venv\Scripts\python.exe -m pc_ontology.evaluation
.venv\Scripts\python.exe -m pc_ontology.quality
```

Оценка создаёт `docs/evaluation/results.json`, `scenarios.csv` и три примера сборок OWL. Сценарии сконструированы для проверки правил: результаты не являются независимой оценкой точности на реальном рынке.

Откройте `ontology/components.owl` или `examples/01-build.owl` в Protégé и запустите HermiT. В приложении логический вывод выполняется на отдельной копии с текущей сборкой; исходный каталог не меняется.

**Внимание:** `python -m pc_ontology.schema` перезаписывает OWL из seed-файлов. Не запускайте генератор поверх нужных ручных правок Protégé без резервной копии.
